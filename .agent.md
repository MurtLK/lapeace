# LAPEACE Agent Orchestration Playbook

Version 1.0 · November 7 2026

## Purpose and operating boundary

This playbook coordinates implementation across agents working in Antigravity, Cursor, ChatGPT, or another available coding environment. It defines shared context, assignments, write boundaries, dependencies, and review requirements. It does not launch or configure those products by itself. A tool without workspace access can produce a proposed patch or analysis for its human owner to apply; it cannot be treated as having edited or tested this repository.

The initial queue is in [coordination/tasks.json](coordination/tasks.json). Task states describe actual work: planning these documents does not mark implementation complete. The first ready tasks are T00 and T60. Do not start every task at once.

## Read at the start of every task

1. The user's current request and any higher-priority environment instructions.
2. [AGENTS.md](AGENTS.md), this playbook, [PRD.md](PRD.md), and [.spec.md](.spec.md).
3. [Objective.md](Objective.md) and the [source project plan](docs/references/LAPEACE%20ElevenLabs%20Project%20Plan.md).
4. Your registry task and its completed dependency handoffs.
5. The source pack's README, DATA_DICTIONARY, and LICENSES when working with data.

For release behavior use the PRD; for schema, API, metric, and index details use the spec. The newer source plan supplies named human roles. If two documents disagree about an interface, report the conflict to the coordinator and keep working only on independent work. Do not silently implement a different contract.

## Provider and workspace setup

- Use the provider, model, environment, and scope named in the assignment. Check connected tool capabilities before claiming that another provider is available. If it is unavailable, report that fact and leave the task unclaimed or blocked; do not silently substitute another provider or launch an external CLI.
- When the current runtime supports cross-provider delegation, use its documented delegation tools. An assignment in this file is not evidence that a provider is connected.
- In Cursor or Antigravity, open the intended repository checkout and paste the startup brief below. In ChatGPT, use a connected workspace-capable coding environment, or request a scoped patch deliverable. For tools that do not automatically read AGENTS.md, explicitly attach or paste the four primary Markdown documents.
- Check the checkout path and branch before edits. On another machine, configure `LAPEACE_DATASET_SOURCE` for its local copy; the `/Users/murtadalakhdar/...` path is specific to this host.
- Use a shared checkout only with disjoint write paths and a coordinator. Separate branches/checkouts are preferable for independent agents; the coordinator assigns and integrates them through the active environment's supported workflow. Do not assume an unrelated checkout shares file locks or task status.
- Do not create new top-level chat threads, launch additional agents, publish, deploy, push, or open PRs unless the task or user authorizes those actions. Implementation tasks authorize their scoped local edits and checks. An agent must not spawn more agents unless its task explicitly permits it.

## Assignment and claim protocol

The coordinator is the only writer of `coordination/tasks.json`, shared contracts, the root dependency files, and integration configuration unless a task explicitly grants those paths. Other agents report status through task-specific handoffs or messages. This avoids multiple agents rewriting the queue or lockfiles.

1. Coordinator confirms all dependencies are `done`, assigns a task ID, actual runtime label, agent/run ID, base commit, and allowed paths, then marks it `claimed`. T00 and T60 have no dependencies.
2. For a shared checkout, create `coordination/claims/<task_id>.json` exclusively, using an atomic create-if-absent operation. Include `claim_id`, `task_id`, `agent_id`, `provider`, `run_id`, `workspace`, `branch`, `base_sha`, `started_at`, and `write_paths`. A task agent may create only its assigned claim. Failure to acquire means stop before editing.
3. Coordinator verifies the claim and marks the task `in_progress`. The agent checks worktree status, preserves others' edits, and changes only the assigned source paths and explicit runtime-output paths. Shared ignored build/test outputs such as environments, `node_modules`, and test caches are permitted where declared in the registry; installing dependencies still belongs to the coordinator. A claim does not authorize broader source edits or arbitrary generated data.
4. On a separate checkout, the coordinator's registry in the control checkout is the assignment authority. Do not treat a local claim in an isolated checkout as a globally exclusive lock. All cross-app launches must pass through the same coordinator or the human relaying its assignment.
5. Report changed files, checks, and blockers in `coordination/handoffs/<task_id>.md`. Mark the work `review` through the coordinator. A lead verifies acceptance before `done`; dependent tasks cannot treat `review` as complete.
6. Coordinator releases the claim only after integration or confirmed cancellation. A stale timestamp alone does not permit takeover: first confirm the old writer has stopped and preserve its diff. Resume uses a new claim ID and a new base review.

No lock service or automatic state synchronizer has been implemented. Until one exists, the coordinator enforces this protocol through explicit assignments and reviews. A filesystem lock protects one shared filesystem only.

Allowed states: `pending`, `ready`, `claimed`, `in_progress`, `review`, `done`, `blocked`, `cancelled`. Pending becomes ready when dependencies are done. Blocked records a concrete reason and owner. Done requires integrated evidence; code generation or a successful mock test alone does not establish real benchmark performance.

## Shared contract changes

T00 materializes `contracts/v1/` from the spec, including success, missing-data, provider-failure, fixture, and replay examples. It adds API-facing TypeScript types and backend models with schema checks. Freeze `schema_version=1.0.0` before T10/T20/T30 begin.

An agent needing a contract change submits a short proposal in its handoff: missing requirement, exact fields/endpoints affected, compatibility impact, and consuming tasks. The coordinator edits the spec, schemas, examples, and types together, records the decision, and notifies consumers. Pause only dependent work. No private schema forks, duplicate API clients, arbitrary endpoint renames, or unannounced new packages.

The coordinator alone updates lockfiles, root scripts, composition roots, README setup, and shared configuration during integration. Agents can propose these changes as patches in handoffs. Do not run simultaneous package-manager installs in one checkout.

Mahar starts with a small CSV/path/required-field checker and a review sheet. Murtada supplies the manifest and expected columns, reviews the checker, and owns any metric or selection change. Mahar may log a questionable reference without guessing its meaning or silently changing it.

## Dataset and provider safeguards

The dataset source is read-only. Extract safely into ignored workspace data; preserve metadata and licence attribution. The archive contains English speech, and its language field identifies first language. Source human speech is not ground truth for safe calls. Do not implement the deferred phishing detector in a foundation task.

Only T70 may submit benchmark STT requests after explicit live mode, a dry-run estimate, configured credentials, and the two-clip smoke inspection. T50 implements the live service capability but automated checks use mocks; a human-coordinated live demo smoke test uses a separate bounded budget and consented or reviewed scenario audio. Do not duplicate paid jobs across providers or agents. Retrieve secrets through the active environment's secure mechanism; never request keys in ordinary chat or commit them.

For no-key development, use small toy examples marked `origin=fixture`. For a no-key presentation, use reviewed cached provider outputs and identify replay. A missing artifact is a visible missing state. No teammate or agent can mark a result measured merely by creating a JSON file with a plausible score.

## Handoffs and release integration

Each task uses [the handoff template](coordination/handoffs/TEMPLATE.md). Keep the report task-specific. Distinguish authored code, checks actually run, mocked behavior, live behavior, and unverified assumptions.

Integrate T00 first; then the completed data/API/UI tasks; then reviewed service and content changes; then generated real evidence. The coordinator resolves shared-file conflicts, verifies schema compatibility, and runs the release checks in the spec. T90 reviews the integrated result without editing another owner's files; small findings return to the appropriate owner or coordinator for repair.

The release report must include the run/settings/manifest identifiers, sample accounting, ward calculation, scenario results, relevant test commands and outcomes, attribution, and any remaining limitation. Do not claim deployment, external-provider execution, or cross-tool synchronization without evidence.
